# 7.0 Shell and section architecture

**Rule:** large documents split into a *shell* (assembly surface) plus *section files* (content). The method below - what a shell holds, how a group grows, the sizes, how to split - is the standard for every project. The layout is an option each shell names in its intro line; a shell that names none is chronological, one file per theme or part.

- The **shell** is the assembly surface; section files hold the content - always edit those. Besides its `![[embed]]` lines, a shell may carry only its H1, a short intro or routing paragraph (name the layout there), an entry template, its grow lines (below), and script-owned marked blocks - a heading or lines a script marks as its own (an HTML-comment marker on the line or around the block) that only that script writes. Entries never live in the shell. A shell's frontmatter carries no edit_log (YAML Schema, edit_log). (Community Stack, DataWizard, 2026-10)
- Section files live in `_Sections - ProjectName/<ShellName>/`, a subfolder mirroring the shell's name. Section folders are siblings of shell folders, not children.
- Shells live in the domain folder appropriate to their content; lightweight projects may keep a shell at the project root.
- Numbering starts at `1.0` (`0.x` is reserved for infrastructure files). Section headers use plain numeric prefixes matching the filenames - no Roman numerals.
- Section YAML carries `parent: "[[Shell Name]]"` and `section: N` (matching the filename prefix); each section file opens with `*Part of the [[Shell Name]]*`.
- **5+ sections** in a document - create the section subfolder rather than leaving the files loose.
- **Layout is an option.** One section file per entry (a decision log numbered by decision id, for example `17.0 D17 - Short title.md`) or one per theme or part; newest-first or chronological reading order. One file per entry suits a new decision log, because an entry never outgrows its file. A themed file still grows, so the growth rule applies to it too. (Community Stack, DataWizard, 2026-10)
- **Growth by continuation files.** The section a group appends to is its *append target*. When the append target reaches the soft size (below), start a continuation: a new section file with the next free number in the group (after `3.3` comes `3.4`; after `3.9`, `3.10`), and add its embed line where the group's grow line says. Never move items to make room and never renumber; file numbers need not match reading order. The continuation opens with `*Continuation of [[<previous file>]]*` under its breadcrumb and repeats the headings that tools read from the group (for example the tier headings a status script keys on). Append-only groups (Done, Deployed, Resolved, Archive) grow the same way: a full section stays as it is and nothing is trimmed. Any session, from any project, may add the embed line for a section it starts in a project tracking shell (0.x files and `_Sections` shells); that embed line and the group's grow line `target` are the only shell-body edits it makes. Seed shells stay under the cross-project canon write gate (15.0). (Community Stack, DataWizard, 2026-10)
- **Grow line.** A shell says where each growing group's new sections go in one comment line, placed just above the group's first embed (reading view hides it):
  `<!-- grow: group=3 target="3.3 Soon - P1 - Follow-ups" insert=after soft=30 -->`
  The line holds space-separated `key=value` pairs; a value with spaces goes in double quotes. `group` (required) is the group's leading number. `target` is the append target's file name without `.md` (default: the group's last embed). `insert=after` puts the new embed line directly below the target's embed (chronological order); `insert=before` puts it directly above (newest-first); the default is `after`. `soft` is the soft size in KB (default 30). A group with no grow line takes all the defaults. A one-file-per-entry group has no append target and needs no grow line; its new embed goes where the intro line says (newest-first: above the first embed). When a continuation starts, set `target` to it in the same edit. Scripts read the grow line; people read the intro line beside it. (DataWizard, 2026-10)
- **Sizes.** Hard limit 50 KB: past it, MCP reads and patches turn unreliable (PI Working Rule 7), so a file at or over it is sectioned or continued now. Soft size 30 KB: an append target starts its continuation, and a shell over 30 KB needs a sub-shell plan (for example one shell per year of a session log). Split target about 25 KB: when you split, cut pieces of about 15-25 KB so each has room to grow. (DataWizard, 2026-10)
- **A SKILL.md is never split with embeds**, because skill loaders read only the SKILL.md text. A skill sections by progressive disclosure: reference files in `references/` beside it, each named by the step that needs it. (DataWizard, 2026-10)
- **How to split safely.** The split is byte-faithful: content moves unchanged, and only the new frontmatter and breadcrumbs are written fresh.
  1. **Plan.** Choose the split points (heading, entry or item boundaries, never inside a code fence) and the file names; a heading becomes a file name only after the Filename Safety clean-up; no two slices may take one name, and a name already on disk stops the plan. Grep the vault for heading and block links into the file (`[[Name#Heading]]`, `[[Name#^block]]`); each one needs repointing to its section file. Record the file's sha256, and post a board claim on it where the vault runs a coordination board (26.0). If the live file no longer matches that sha256 when you write, a parallel session has changed it: plan again.
  2. **Slice by script**, never by retyping: exact line ranges or anchors, written to scratch.
  3. **Prove the rejoin.** Assert that the slices, joined in order, equal the original body byte for byte (sha256 on both sides), and count lines, checkbox items and headings on both sides.
  4. **Keep a pre-split copy** per Archiving (10.0), in the archive mirror and never beside the original: a new file at `xArchive - ProjectName/<working folder>/<file name>.pre-<session>.bak`, where a nested working folder keeps its whole path inside the project, so two folders with the same name never collide. Never deleted.
  5. **Write the section files first**, under fresh names, then verify each on disk: re-read it, compare its sha256 with the slice, and YAML-parse its frontmatter. Until the shell is written the original still holds everything, so an interrupted run loses nothing. (DataWizard, 2026-06)
  6. **Write the shell last**, then re-read it and parse its frontmatter. An edit_log the original carried stays whole in the pre-split copy (step 4; never deleted) and is not copied into the shell or any section file: the shell gets an `origin:` line naming the split and no edit_log, and each section file starts its own edit_log window with the split as its first line (YAML Schema, edit_log).
  7. **Repoint** the links found in step 1, release the claim, and record the split (files, bytes, sha256) in the session log.
  Migrating a flat session log follows the same steps. A flat log that holds one entry twice (a brief entry and a fuller one written later the same day): section the fuller one and note the other in the split record; the pre-split copy keeps both. When a splitting script ships, it implements these steps. (ReWoven, Weave, Community Stack, Kosmosis, DataWizard, 2026-07 to 2026-10)
- Empty folders can't be deleted via MCP (the vault FUSE mount blocks it); when files are moved out, the human deletes the empty folder manually in Obsidian.

**Example:** `0.2 Session Log - DataWizard.md` is a shell of `![[...]]` embeds; each entry is a file in `_Sections - DataWizard/Session Log/`, numbered from `1.0`.

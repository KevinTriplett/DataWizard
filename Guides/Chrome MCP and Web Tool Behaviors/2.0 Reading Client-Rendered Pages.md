# 2.0 Reading Client-Rendered Pages

Pages that render client-side (JS apps) may expose little or nothing to a plain fetch or a naive page read. Three working recipes, in escalating order of effort:

1. **Hash-anchor + scroll-screenshots.** Navigate to a hash anchor and take scroll-screenshots section by section rather than expecting full text from a single fetch. Worked on client-rendered fundraiser/leaderboard pages. (Source: RW S28)
2. **Render-wait + `innerText` slices.** For heavily client-rendered app pages (e.g. Bubble apps) that defeat `web_fetch` entirely: Chrome `navigate`, wait ~8s for render, then pull text in slices via `javascript_tool` reading `document.body.innerText`. The tool's output truncates around ~1KB (longer results end in `[TRUNCATED]`), so slice the string across multiple calls. Faster for large text: keep the data in `window.__x`, replace the page body with `<article><pre id=dump></pre></article>`, set its `textContent` to the dump, and read it with `get_page_text` (about 30 KB in one call); a navigation clears `window.__x`, so dump before navigating. (Source: RW S31; LocationScout, 2026-10)
3. **Know which sites fetch fine.** Not everything needs the browser: e.g. Substack subdomains fetch cleanly with `web_fetch`. Try the cheap fetch first. (Caveat: Substack landing/about pages can still be JS-rendered - a subject's bio may live on their wiki/site while the worldview lives in the Substack posts. (ReWoven, 2026-09))
4. **Force verbatim output from `web_fetch`.** For public-site copy, the fetch tends to summarize; an explicit no-summarizing instruction ("return the page text verbatim") gets the actual copy. (ReWoven, 2026-08)
5. **SPAs can drop the path/query on load, and data can hide in hover states.** The built-in browser may land a deep URL on the app root - click through in-page and read visually instead of re-fetching. Some figures exist only in chart tooltips (hover the data point), invisible to every text-read path. (ReWoven, 2026-09)
6. **Robots-blocked source: hand it to the operator's Web Clipper.** When `web_fetch` returns 429/refuses and both Chrome paths are unavailable, the reliable last rung is asking the operator to clip the page into the vault (Obsidian Web Clipper, `_Clippings/`) and reading the clipping. (ReWoven, 2026-08)
7. **`get_page_text` returns Chrome's auto-translated text.** With translation on, a German site's dump came back in English. Quote original-language text from a direct read of the detail page, not from the dump. (LocationScout, 2026-10)
8. **Scraping recipes: check selectors on the first run, and try embedded state JSON first.** Site layouts change between sessions: on one listings site the card markup changed and the old selectors returned 0 cards with no error. A first-run sanity check (card count > 0, one leaf-element dump of one card) catches this in one call. Before DOM scraping, try the page's embedded state JSON (a `<script id="...state...">` block, or an in-page `fetch` of the page URL plus `DOMParser`) - on one rental portal it carried all results with coordinates, totals and page cursors, with no clicking or scrolling. (LocationScout, 2026-10)
9. **A fetch that returns only the title and meta description means "unreadable", not "no evidence".** On a JavaScript-rendered site, `web_fetch` and plain fetches can come back with only the page title and meta description, and no body. Do not report "nothing found" from such a fetch as an absence of evidence: read the site with the browser (rungs above) or ask the project that owns the source. (Community Stack, 2026-10)
10. **`get_page_text` can return only a sidebar teaser while the article is still in the page.** On one magazine site `web_fetch` answered "Access Denied", and `get_page_text` returned only a teaser from a sidebar. A `javascript_tool` walk recovered the full article. Start at the `h1`, go up to the first ancestor whose `innerText` is long, and read that text in slices of about 950 characters (the tool truncates near 1000; see rung 2). (Community Stack, 2026-10)

This ladder is the standing home for the recurring "JS-rendered surface needs a live browser" family - try the cheap fetch, then render-wait reads, then in-page click-through, then the operator clip; a source that defeats all rungs is flagged unverifiable rather than guessed at.

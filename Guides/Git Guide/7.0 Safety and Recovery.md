# 7.0 Safety and Recovery

Git never truly deletes anything. Every commit is a permanent snapshot. Even after a bad merge, the previous state is preserved and recoverable.

## How Git Protects You

- **Every commit is a snapshot.** You can always go back to any previous commit and see or restore every file as it was at that moment.
- **Merges are reversible.** A merge commit records both "before" states. You can undo a merge after the fact.
- **Branches are cheap bookmarks.** Creating a branch before risky work costs nothing and gives you a named save point.
- **Reflog is the last resort.** Even if you do something that seems destructive (reset, rebase, force-push), git's reflog records every state your local repo has been in for at least 30 days.

## Rolling Back a Bad Merge

Scenario: a branch was merged to main, but the changes caused problems.

### Step 1: Find the merge commit

```bash
git log --oneline --merges -5
```

You'll see something like:

```
a1b2c3d Merge branch 'restructure-2026-04-23' into main
```

### Step 2: Revert the merge

```bash
git revert -m 1 a1b2c3d
```

The `-m 1` tells git "keep main's version, undo the branch that was merged in." This creates a new commit that undoes the merge -- it doesn't erase history, it adds a correction on top.

### Step 3: Push the revert

```bash
git push origin main
```

Everyone who pulls will now get the reverted state. The merge commit and the revert commit both remain in history -- nothing is lost, and you can see exactly what happened.

## Viewing Files from Before a Merge

If you just want to see or copy files from before the merge without reverting everything:

```bash
git log --oneline -10                              # find the commit before the merge
git show <pre-merge-hash>:path/to/file.md          # view a specific file at that point
git checkout <pre-merge-hash> -- path/to/file.md   # restore a specific file
```

Or create a temporary branch to browse the entire pre-merge state:

```bash
git checkout -b pre-merge-snapshot <pre-merge-hash>
```

When done, switch back: `git checkout main`

## Restoring a Single File

```bash
git log --oneline -- "path/to/file.md"         # find the last good commit
git checkout <hash> -- "path/to/file.md"        # restore that version
```

The file is now restored in your working directory. Next auto-sync will commit the restoration.

## Undoing Your Last Commit

If you haven't pushed yet:

```bash
git reset --soft HEAD~1
```

This undoes the commit but keeps your changes as uncommitted files -- you can re-edit and recommit.

If you already pushed:

```bash
git revert HEAD
git push origin main
```

This adds a new commit that undoes the previous one. Safer than rewriting history on a shared branch.

## Rolling Back to a Safety Tag

If you created a `pre-merge-backup` tag before merging (see Section 6):

```bash
git checkout pre-merge-backup              # inspect the state
git checkout main                           # back to current main
git revert -m 1 <merge-hash>              # revert the merge (preferred)
```

Or, for a hard rollback (use with caution on shared repos):

```bash
git reset --hard pre-merge-backup
git push --force origin main
```

Force-push rewrites shared history -- only do this if all collaborators are aware and have no unpushed work.

## Git Surgery on a Live, Auto-Synced Repo

When a Mac-side auto-sync (DW Save / Obsidian Git on a cron) is committing and pushing in the background, doing history surgery from a sandboxed agent environment needs care:

- **The sandbox and the Mac share the working tree.** Auto-sync commits and pushes sandbox file changes mid-session. Stale `.git` lock files left by a Mac git process cannot be unlinked from the sandbox, but ref updates still succeed. Plan git work around the sync schedule rather than fighting it.
- **Safe history-rewrite sequence** (used for the 2026-06-10 Seed secret removal): mirror-clone the repo to `/tmp`, run `git filter-repo` on the mirror, then in the live repo `git fetch` the rewritten objects and `git update-ref` the branch to the new history. Force-push BEFORE the next auto-sync pull fires, or the old history reattaches. Always capture a backup ref (a tag on the pre-rewrite HEAD) first.
- **Never** recover a rewritten repo with a merge (`git pull --allow-unrelated-histories`) -- that reattaches the history the rewrite removed. Recover via "Recovering a Seed Clone (Remote-Agnostic)" below: canonical-by-URL, ff-only first, reset only after triage.

## Recovering a Seed Clone (Remote-Agnostic)

Use this procedure for ANY broken, stale, or diverged Seed clone: an unrelated-histories error after an upstream history rewrite, a clone that seems months behind, a fork that drifted, or any case where you are not sure what state the clone is in. This is the single safe recovery path -- other docs (the VERSION.md rewrite NOTICE, 9.0 Troubleshooting) point here rather than restating it.

**Why remote-agnostic:** recovery recipes that name `origin` assume `origin` is the canonical repo (`github.com/andrewalan11/DataWizard`). On a fork-shaped clone -- `origin` pointing at a personal fork, `upstream` at canonical -- `git reset --hard origin/main` silently rolls the Seed back to the fork's stale state and reports success. The camouflage is total: the ahead/behind numbers reproduce the exact signature the recovery targets, and a "no local work" check passes clean when the divergence is entirely other people's commits (a 2026-08-30 near-miss came within one declined command of downgrading a collaborator's Seed by two minor versions this way). Always identify the canonical remote by URL, never by name.

### Step 0 -- mandatory backup (unconditional, before any recovery command)

```bash
git branch backup/pre-recovery-$(date +%Y%m%d-%H%M)
git status --porcelain
# if the status output is non-empty:
git stash push -u -m "pre-recovery $(date +%Y%m%d-%H%M)"
```

The branch preserves committed state; the stash preserves uncommitted and untracked edits, which `reset --hard` destroys silently. Undo of anything below = `git reset --hard backup/pre-recovery-<stamp>` then `git stash pop`. No exceptions -- this is what makes every later step reversible even if mis-applied.

### Steps 1-5 -- the recovery tree

```
STEP 1  git remote -v
        Identify the canonical remote BY URL (github.com/andrewalan11/DataWizard),
        never by the name "origin". If no remote matches:
        git remote add canonical https://github.com/andrewalan11/DataWizard.git
        Call the matching remote <C> below.

STEP 2  git fetch <C> --prune
        (comparing against stale refs is its own trap -- always fetch first)

STEP 3  git merge --ff-only <C>/main
        SUCCEEDS -> done; go to Step 5. Success proves there were no local-only commits.
        FAILS    -> real divergence. Do NOT reset yet; go to Step 4.

STEP 4  Triage, human in the loop:
        git log --oneline <C>/main..main     # full, UNFILTERED list of local-only commits
        git merge-base main <C>/main || echo "UNRELATED HISTORIES"
        git stash list
        git branch -a
        - Unrelated histories matching a known upstream rewrite (see the VERSION.md
          NOTICE for the current one) -> git reset --hard <C>/main
        - ANY commit not explainable as a pre-rewrite duplicate -> STOP:
          git branch save/local-work, ask a human, then reset and cherry-pick
          what should survive.

STEP 5  Verify: git status ; git log -1 --oneline
        Compare the seed: version in VERSION.md before vs after. If it went DOWN,
        stop and investigate -- a downgrade is legitimate only when deliberate.
```

**Rule of thumb: back up, fetch canonical, ff-only. If ff-only refuses, stop and triage -- reset only what a human has looked at.** `--ff-only` can never discard a commit and fails closed on real divergence; reset is never the entry point. (The older "reset, never merge" rule was about merge commits reattaching rewritten history -- it does not ban fast-forwards, which create no merge commit and cannot reattach anything.)

**Do not:**

- Use an author-filtered commit list ("no commits of yours") to approve a reset. It fails open on fork divergence, commits made under a different email (git plugins, GUI clients), and shared local-only work. The unfiltered `<C>/main..main` list plus a human is the gate; the author view is escalation-only ("these look like yours -- stop").
- Reach for `reset --hard` with a "corrected" remote name as the first move. ff-only first, always; reset is the triaged last resort.
- Recover with `git pull --allow-unrelated-histories` or any merge-commit strategy after an upstream rewrite -- that reattaches the removed history.
- Repoint a fork's `origin` to canonical as part of recovery. Remote layout is a per-operator decision made separately -- never a recovery side effect, a batch action, or a script default.

**Destructive steps need a second reviewer:** no `reset --hard` runs on one Claude instance's say-so -- propose the plan on paper and get a second instance's (or a human's) review first (DW D109).

## Nuclear Option: Full Vault Rollback

If everything is broken and you need to go back to a known good state:

```bash
git log --oneline -20                       # find target commit
git reset --hard <commit-hash>
git push --force origin main
```

This is destructive -- all changes after the target commit are permanently lost from the branch (though git reflog preserves them locally for 30 days). Only use for genuine recovery.

## Using Reflog (Last Resort)

If you've done something that seems to have lost commits:

```bash
git reflog
```

This shows every state your local repo has been in, even after resets and rebases. Find the hash of the state you want and:

```bash
git reset --hard <reflog-hash>
```

## "Oh No" Quick Reference

| Scenario | What to do |
|---|---|
| Merged a bad branch to main | `git revert -m 1 <merge-hash>` then `git push` |
| Need to see a file from before a merge | `git show <pre-merge-hash>:path/to/file.md` |
| Accidentally deleted a file and committed | `git log --oneline -- "path/to/file.md"` then `git checkout <hash> -- "path/to/file.md"` |
| Want to undo my last commit (not pushed) | `git reset --soft HEAD~1` |
| Pushed something I shouldn't have | `git revert HEAD` then `git push` |
| Everything is broken | Restore from Time Machine / File History, or `git reflog` to find a good state |
| Merge conflict I don't understand | Open the file, look for `<<<<<<<` markers, keep the version you want, delete the markers, save |
| "Another git process is running" (stale lock) | Quit Obsidian or confirm no git is running, then `rm -f .git/index.lock` and retry. See 9.0 |
| Push rejected, "fetch first" | `git pull --no-edit && git push`. See 9.0 |
| Conflict markers got committed (auto-sync) | `grep -rl '^<<<<<<<' . --include=*.md` to find them, then resolve and commit. See 9.0 |
| Two people editing the same file | Communicate. If conflict happens, resolve together -- git preserves both versions |
| Created a tag before merge, now need to roll back | `git revert -m 1 <merge-hash>` (safe) or `git reset --hard pre-merge-backup` (destructive) |
| Seed clone broken, stale, or "unrelated histories" | See "Recovering a Seed Clone (Remote-Agnostic)" above -- back up, find canonical by URL, ff-only first |

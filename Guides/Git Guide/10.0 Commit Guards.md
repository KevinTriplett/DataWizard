# Commit Guards

Two guards keep bad content from syncing into a shared repo:

- **Conflict markers** - unresolved merge markers (the `<<<`, `===`, `>>>` triples) that auto-sync can otherwise commit silently, corrupting a file for everyone who pulls.
- **Windows-unsafe filenames** - names that break a teammate's pull on Windows: a trailing space or dot, the reserved characters `? : * " < > |`, control characters, or reserved device names (CON, PRN, AUX, NUL, COM1-9, LPT1-9).

Each guard runs in two places: a **local pre-commit hook** (commit-time - stops it before it leaves your machine) and a **CI check** (push-time - the visible backstop for anyone who has not installed the hook).

## What ships in the Seed

| File | Role |
|---|---|
| `Seed/Scripts/hooks/pre-commit` | The hook. Runs both guards on staged changes; blocks the commit if either fires. |
| `Seed/Scripts/install-git-hooks.sh` | One-time per-clone installer. |
| `Seed/Scripts/ci/check-conflict-markers.yml` | CI workflow for conflict markers. Filenames are covered by a sibling `check-filenames.yml`. |

## Install the pre-commit hook (once per clone)

Git hooks live in `.git/hooks/`, which git does **not** sync - so the hook has to be installed in each clone, and every operator on a shared repo installs it on their own machine.

```
bash "<vault>/_DataWizard/Seed/Scripts/install-git-hooks.sh" "<path-to-repo>"
```

The installer copies the hook in, makes it executable, and adds `SYNC-BLOCKED.md` to the clone's `.git/info/exclude`. Re-run it after a Seed update to pick up an updated hook.

## Shared team repos: vendor the hook instead (recommended for teams)

For a repo shared by several operators, prefer committing the hook into the repo over the per-clone copy above. The copy approach means every operator has to re-run the installer whenever the hook changes - the step most likely to silently not happen. Vendoring avoids that:

1. Commit the hook to `.githooks/pre-commit` in the repo (a copy of `Seed/Scripts/hooks/pre-commit`), and `chmod +x` it before committing.
2. Add `SYNC-BLOCKED.md` to the repo's tracked `.gitignore` (once).
3. Each operator runs this one line once, in their clone:

```
git config core.hooksPath .githooks
```

Because `.githooks/` is a tracked folder, the hook syncs to every clone and updates propagate on the next pull - no reinstall, and no dependence on each operator keeping their Seed current. The only per-clone step is the one-time `core.hooksPath` setting (git will not use a tracked hooks folder without it). Verify it with `git config --get core.hooksPath` (expect `.githooks`).

## What happens when a guard fires

The commit is blocked. Because most commits in a DW vault are unattended (the Obsidian Git timer, the launchd sync script), a silently-blocked commit could become an invisible sync stall - so on a block the hook writes **`SYNC-BLOCKED.md`** at the repo root. You will see it in Obsidian's file list. It names the problem and the offending files in plain language, and it clears itself automatically on the next clean save.

To bypass a genuine false positive once:

```
git commit --no-verify
```

## The conflict-marker whitelist

The conflict-marker scan skips anything inside a fenced code block (three backticks or `~~~`), so conflict-resolution tutorials that show example markers do not trip it. This is fence-state tracking, not a hardcoded file allowlist - future tutorials are covered automatically. The one rare false positive is a genuine setext heading underline of exactly seven `=` characters outside a fence; bypass it with `--no-verify` if you ever hit it.

The scan also skips `.obsidian/` trees (matched as `.obsidian/*|*/.obsidian/*`) -- Obsidian workspace and plugin state, not authored content. A plugin's bundled JS can legitimately contain conflict-marker strings (e.g. the Obsidian Git plugin's own `main.js`), which would otherwise false-positive on every plugin update on any vault that tracks `.obsidian/`.

## Install the CI check

Copy `check-conflict-markers.yml` into the repo's `.github/workflows/`. It runs on every push and on manual dispatch, and fails the run (with per-file annotations) if any tracked file carries markers outside a fence. It mirrors the existing filename check so both failure modes are guarded at both commit-time and push-time.

## Already committed a marker?

These guards are prevention. If markers have already reached the repo, see [[9.0 Troubleshooting]] for recovery.

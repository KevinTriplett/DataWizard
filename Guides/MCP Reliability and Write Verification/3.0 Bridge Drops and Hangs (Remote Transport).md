# 3.0 Bridge Drops and Hangs (Remote Transport)

Distinct from a 502 on a single write, the remote bridge itself can fail in two ways, both of which take out *all* MCP calls rather than corrupting one: a **tool-registry drop** (calls return "not found" immediately, no hang) and a **multi-minute hang** on a call. Both recover by quitting Claude Desktop from the tray and relaunching. A mid-session registry drop can also recover via `RefreshMcpTools` once the desktop app reconnects, without a full relaunch. Observed ~3x in one session with no partial writes -- verify-after-write held throughout, so a dropped or hung call is an availability problem, not silent corruption. (Source: Weave, 2026-08)

In a remote (cloud) Cowork session the same event has a **lazy-loading variant**: an MCP server disconnect/reconnect drops the session's already-loaded tool schemas, so a previously working tool returns "No such tool available" even after the server reports connected again. No relaunch needed -- re-run the tool_search load for the tools you need and continue. Treat the first such error after a reconnect notice as a reload signal, not a missing capability, and re-load the full set you'll need in one call rather than one at a time. (Source: Rootland, 2026-09) The same error also arrives with no reconnect notice at all: the Obsidian tools flip mid-session from the `claude-device` namespace to `remote-devices__obsidian__*`, and a call fails with "No such tool available ... call mcp__remote-devices__obsidian__* instead" - after a ~125 s timeout on a first read, at the first write after orientation, or after a desktop-app restart. A `ToolSearch` for the `remote-devices__obsidian__*` tools fixes it, and the `remote-devices` set then works for the rest of the session; at orientation, load the `remote-devices` Obsidian set first. (Evolutionary Media Commons, 2026-10) A write call that fails DURING the drop with an explicit "device ... is not connected to the bridge" error is a clean failure, unlike the 502 case: in the observed instances nothing was written. Still confirm-unwritten before retrying (Working Rule 5 / the 502 discipline) - after reconnect and reload, a single retry landed each patch with matchCount 1 and no duplicates. (Source: Rootland, 2026-09)

Files already staged into the container survive a mid-session drop, so plan around the drop - wait for the reconnect, reload the tools, then continue from what is staged - rather than retrying calls into a dead bridge. (VibeCut, 2026-08)

**Local MCP tools time out while the computer sleeps - or, with it awake, until the desktop app restarts.** When the operator's machine is asleep, or has just woken and the session has not yet re-linked, every call to an MCP server that runs on that machine (local Obsidian or filesystem servers) waits about 120-137 s and fails with "No result received from client-side tool execution" or no response at all - even a trivial call such as `list_allowed_directories`. Retrying does not help. Stop after the first such timeout (two at most), ask the user to wake the machine, and once the session re-links continue on the `remote-devices` tools (obsidian, filesystem, `device_bash`, `device_request_folder_access`), which answered at once in both field cases. Treat the first reads after the wake as wake-stale (Known Issues) and verify freshness before acting on them. (Evolutionary Media Commons, 2026-10; MetaMyth, 2026-10) The same timeouts also hit with the computer awake: every `claude-device` Obsidian and filesystem call timed out (~120-135 s each, five calls in a row) until quitting and reopening the Claude desktop app fixed it at once. After two timeouts with the computer awake, ask the operator to restart the desktop app before anything else. (Evolutionary Media Commons, 2026-10)

# 8.1 Device Bridge - Staging, Commits and Transport

*Split from [[8.0 Device Bridge]] in DW-S408; shell and environment behaviors stay there.*

- **`device_commit_files` rejects an explicit `expectedMtimeMs: null`** -- omit the field entirely when no mtime guard is wanted. (Source: DW S229)
- **Deliver a git repo to the user's machine when `device_bash` has no network:** clone (shallow) in the cloud sandbox, `tar czf`, `SendUserFile` -> `device_commit_files` into the destination folder, then `tar xzf` with `device_bash` (the `.git` survives, so `git log`/`remote` work locally). ~12 MB tarballs land fine; park the tarball in a `_to_delete/` subfolder afterwards since the device shell cannot delete. (Source: VibeCut S77, 2026-08)
- **Probe the device shell's network before taking the tarball route.** The recipe above rests on a premise that depends on configuration: in another configuration `device_bash` reached GitHub and a direct device-side clone worked (with the delete grant - see the Dropbox `config.lock` bullet under Git on a Cowork-Mounted Folder). One `curl -sI https://github.com` in `device_bash` decides which path to take. (VibeCut, 2026-09)
- **Reader bundle - the reverse direction, for parallel readers:** `tar czf` the vault folders a research pass needs into a `_to_delete/` subfolder on the Mac, stage that one file, extract it in the container, and run several Opus readers in parallel on the clean copies with no bridge calls at all. The vault is untouched, the bridge carries one file instead of hundreds of reads, and the readers cannot write back by accident. (DataWizard, 2026-10)
- **Bundles in either direction, and `tar --overwrite`.** One `.tgz` beats per-file staging both ways: write it into a connected folder and stage that single file in, or commit one bundle out and unpack it on the device, with an md5 list for the text files committed beside it and checked after unpacking. With deletion off, `tar xzf` over existing files fails on each with "Cannot open: File exists" (tar unlinks before writing); `tar xzf ... --overwrite` writes in place and works - always pass it when unpacking over vault files. (Evolutionary Media Commons, 2026-10)
- **The executable bit does not survive a bundle from the vault into the container.** After unpacking a `tar` made on the device from the vault, `./build_all.sh` gave "Permission denied"; run staged scripts as `bash <script>`. (Evolutionary Media Commons, 2026-10)
- **`device_commit_files` writes files with mode 0600, so a committed script loses its execute bit.** A script installed this way shows `-rw-------` on the Mac and cannot run as a program. Put a `chmod 755 "<script>"` step in every script install, and check the mode afterwards (`ls -l`, or `git ls-files -s` for a tracked script: `100755`). Do not read "written" as "ready to run". (DataWizard, 2026-10)
- **`device_commit_files` re-sends the FIRST version of a reused `stagedPath`.** Committing an edited file under an outputs path that was already committed earlier in the session delivered the original bytes again (the call still reported "written"); a test run then exercised the stale script. Write each iteration to a NEW name (`script.v2.sh`, `.v3.sh` ...), commit that, and compare `md5sum` on both sides before running anything (text files - see the checksum rule below). The same-path staleness exists in the staging direction too (MCP Reliability guide, Known Issues). (Source: DataWizard, 2026-09; confirmed Rootland, 2026-09 - a re-commit of edited JSON under a reused outputs path reported "written" and even updated the device mtime, but delivered the original bytes; a fresh staging path fixed it, and cross-side `md5sum` comparison is the only trustworthy check. Confirmed again (Community Stack, 2026-10; LocationScout, 2026-10; Kosmosis, 2026-10 - twice in one session, each time reported "written", caught by a device-side sha256); the defect is intermittent - one LocationScout run saw three same-path re-commits arrive correct - so a clean run proves nothing: always use fresh names.) `force: true` does not bypass it: a commit with `force: true` reported "written" while the vault file kept its older content (the same note committed twice within minutes); a second commit of a freshly staged copy landed. Check the vault file's checksum after every commit, not the tool's result. (Evolutionary Media Commons, 2026-10)
- **An edited outputs file can commit as its pre-edit copy on the FIRST commit, not only on path re-use.** A builder copied staged files into an outputs path, edited them there, and committed each path once: 4 of 13 files landed as the pre-edit copy or a part-edited one, and each call reported "written". Fix: write the final version to a fresh outputs path, commit that, then compare the on-disk size (or checksum) with the local copy. A first commit of an edited file is not proof either. (DataWizard, 2026-10)
- **Never commit a file in the same parallel tool block that edits it.** A container Bash edit of a file under `/mnt/user-data/outputs/` and a `device_commit_files` for the same file, issued together, can race: the commit shipped the pre-edit bytes and a second commit was needed. Edit, then commit in the next call (under a fresh name, per the bullet above), then verify on the device - a parse or a grep for the changed value - before anything downstream reads it. (ReWoven, 2026-10)
- **Standing rule: checksum-verify every batch commit, device-side, for text files.** After each `device_commit_files` batch, compare an md5 (or sha256) list from the container with `md5sum -c` on the device - one call. Do not hash-check binaries: PNG and JPEG files can arrive as the same image with different bytes (PNGs 2-3 percent larger; one JPEG ~25 percent), likely a re-encode in transit, while text in the same call matches. Check code and data; treat images as lossy in transit. A clean check proves only the files on the list: one builder's commit list left out a release file and the md5 check still passed, so after a commit also compare the folder listing (workspace vs vault). (LocationScout, 2026-10; Holonic Canvas, 2026-10; Evolutionary Media Commons, 2026-10)
- **Staging and commit paths and limits.** `device_stage_files` stages only from connected folders: a file in the device shell's `$HOME/mnt/outputs` scratch folder was refused ("not inside a folder connected to Cowork") when `get_device_info` listed no scratch folder - copy it into a connected folder first and stage it from there - and a file more than 7 folders below a connected folder is refused as "too deeply nested" (a folder request cannot shorten that - copy it to a shallow path, or read it in the device shell). `device_commit_files` takes `stagedPath` only under `/mnt/user-data/outputs/`. Both take at most 50 files per call; past that, use one bundle (above). With no scratch folder, park transfer bundles in the project's `_to_delete/` subfolder. To land a large note in a project folder that is not connected, commit it into a connected folder and then `move_note` it there with the Obsidian MCP - no retyping a 19 KB note into a tool call (`move_note` does not rewrite links - MCP Reliability 12.0). (Evolutionary Media Commons, 2026-10; Holonic Canvas, 2026-10; Kosmosis, 2026-10)
- **With the device shell down, `device_commit_files` still writes new files, and it avoids retyping long ones.** Build the file in the container's outputs folder (for example frontmatter plus a `cat` of the report body). Then commit it with `stagedPath` to a path in a connected folder. The result is a byte copy: no hand retyping and no truncation risk. This archived two long review reports word for word while every `device_bash` call failed. The filesystem MCP `write_file` also works, but it needs the whole text inside the tool call. Commit each new file under a fresh name and check its checksum, as above. (Rootland, 2026-10)
- **`device_stage_files` fails the whole call when one listed path does not exist.** No file is staged, not even the ones that exist. List the folder with `device_list_dir` first, or send the call again without the missing path. (DataWizard, 2026-10)
- **If the bridge drops mid-session, keep building in the container and commit after reconnect.** The `remote-devices` tools can vanish for about an hour (seen after a long sub-agent run) and return when the operator reopens the desktop app; container work and sub-agents on container copies carry on meanwhile. After reconnect, `device_commit_files` to the same connected folders worked at once with no new grant, and the Mac-side session claim stub was untouched. While the bridge is down, tell the operator nothing is saved yet; if the session must close first, list the uncommitted files in the handoff. Recovery steps for the drop itself: MCP Reliability guide, Bridge Drops and Hangs. (Rootland, 2026-10)
- **Commits to an external Mac drive leave `._*` AppleDouble files.** Committing from the cloud sandbox to a folder on an external drive created a `._<name>` sidecar beside each written file. They are macOS metadata and harmless - not corruption and not a failed write; exclude them when counting or hashing the written files. (VibeCut, 2026-08)
- **Transport a multi-file edit script to the device without staging: base64 it.** A parse-guarded Python edit (frontmatter `edit_log` appends, section inserts across several vault files) runs cleanly device-side, but `device_bash` cannot see the sandbox's `/tmp`. Encode the script in the sandbox (`base64 -w0`) and decode it inside the `device_bash` command (`echo '<b64>' | base64 -d > script.py && python3 script.py <vault-path>`); an ~8KB script transports without issue, and the whole batch lands in one call with one verification pass. (Source: DataWizard, 2026-08)

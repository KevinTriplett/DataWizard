# 8.2 Device Bridge - Sub-agents and Orchestration

*Split from [[8.0 Device Bridge]] in DW-S408; shell and environment behaviors stay there.*

- **Workflow (multi-agent orchestration) tool: `args` arrived `undefined` once; subagents can reach the device bridge.** In one run the value passed as the Workflow's `args` input never reached the script (`args` was `undefined` inside it); inlining the data as constants in the script body is the reliable fallback, and a quick `log(JSON.stringify(args))` at the top of the script tells you which case you are in before any agent spends tokens. Separately, foreground Workflow subagents CAN reach the `remote-devices` bridge (vault reads, `device_bash`) by loading the tools via ToolSearch inside the subagent - the bridge is not restricted to the main loop. (Source: DataWizard, 2026-07) The same holds for `Agent`-tool sub-agents (DataWizard, 2026-10): a worker reads, runs and writes on the Mac through `device_bash` directly, with no staging round-trip. The lead's brief must forbid Read, Write, Edit and Bash by name - those hit the container, not the Mac, and return confident 'file not found' results against vault paths. Background general-purpose sub-agents also reached the Projects tool (`project_read` of .md and .docx project files) and the `mcp__remote-devices__obsidian__*` / `filesystem__*` tools after loading them with ToolSearch, so source content need not pass through the lead's context; a shared conventions file in the scratchpad, read by every ingest agent, kept four parallel agents consistent. (MetaMyth, 2026-10)
- **With `device_bash` down, a sub-agent can still read the Mac through the filesystem MCP.** A general-purpose sub-agent loaded `filesystem__read_text_file` (and list and search) with ToolSearch. A read-only audit of six files (about 5,000 lines) and a context-free review of a build prompt both ran this way. Tell the agent to read large files in head and tail chunks. (Rootland, 2026-10)
- **A device-shell-only worker is the right shape for a delegated batch rewrite.** A Sonnet sub-agent given only `device_bash` wrote a Python script through a quoted heredoc, applied a frontmatter block to 32 vault notes with text-level inserts (no YAML re-dump), kept a backup of each file in the device shell's `$HOME`, and verified every file by re-parsing its YAML and comparing the body with the backup - one tool call, about 30 seconds, no failures. Shape: the plan file lives in the vault (committed and verified on the device first), the script is the executor, and the worker returns only the verification summary. The device shell's `$HOME` is scratch outside the connected folders and invisible to the user - fine for backups and scripts, never for deliverables. The per-file write invariant lives in **MCP Reliability and Write Verification** (Bulk Frontmatter Backfills). (ReWoven, 2026-10)
- **A fast-tier sub-agent can run the bridge's stage and commit tools.** With `device_bash` down, a lead gave the mechanical bridge work to fast-tier helpers. They staged 222 notes (5 calls of up to 50 paths each). They also committed 40 files, then re-staged them and compared md5. Both jobs worked, and the path lists stayed out of the lead's context. The lead first wrote each path list to a JSON file in the scratchpad. Give the helper the file name, not the list. Compare the staged count with the source listing, as in the count-check bullet below. (Community Stack, 2026-10)
- **A sub-agent launch rejected or cancelled at the approval prompt, or killed by the spend limit, may still have run.** The tool result says "rejected", but the agent can already have written files (one case left ~70 in the workspace, another a probe file in a working clone, a third 19 PNGs and a prototype). Before relaunching the same chunk, check disk state (`git status`, the outputs folder) and tell the next agent what is there; a relaunch told to finish from there completed in one pass. Seen four times (Evolutionary Media Commons, 2026-10; Holonic Canvas, 2026-10); the reviewer side lives in the `supervised-build` skill. A sub-agent killed by the monthly spend limit (HTTP 429 "You've hit your monthly spend limit", no hand-back) had likewise already written its output: a complete vault note in one case, a complete review note plus a proposed patch in another. Re-run only what is missing, and switch model tier rather than retrying the same one: a relaunch on the same top tier ten minutes after the limit was raised failed with the same error, while a launch on the default tier worked. The Agent tool's error reads the same before and after the user says credits are enabled. (MetaMyth, 2026-10; Holonic Canvas, 2026-10; Evolutionary Media Commons, 2026-10)
- **An agent stopped by a 529 (server overloaded) error can be resumed with SendMessage.** Tell it to check disk state first rather than trust its last in-memory state. (Evolutionary Media Commons, 2026-10)
- **Resume the builder by message to apply an independent review.** A worker-tier builder wrote its output with a generator script that also checked every quote verbatim against the sources and refused a banned word. A synthesis-tier reviewer that never saw the build wrote a review file. The lead then resumed the builder with `SendMessage` to apply the findings and re-run the generator. 20 findings landed in one pass and the quote check stayed green. Keep the check inside the generator so a fix pass cannot silently break it. This is the inverse of resuming the plan reviewer for verification (`supervised-build` skill, In-thread variant). (MetaMyth, 2026-10)
- **The `Plan` agent type is read-only, including Bash writes.** Asked to save its report to a file, it refused (no new files). Use `general-purpose` for a planner that must write a plan file, or have the main session write the report. (Evolutionary Media Commons, 2026-10)
- **A general-purpose sub-agent usually will not write a report-type `.md` file.** Its own standing instructions forbid report, summary, findings and analysis `.md` files and tell it to return findings in its hand-back; it may describe this as "the harness refuses report `.md` files". Other files land fine (a README and a `.txt` commit list in the same run). Ask for the report in the hand-back, have the lead write it, or name the file as data (`.txt`, `.json`). The data route held: worker-tier sub-agents wrote valid JSON files in the cloud workspace 6 of 6 times when the brief asked for JSON only and the lead rendered and checked the notes. It did write a `.md` when the file was the named deliverable: the prompt said the file is the deliverable, writing it is required, and the full text should come back if it cannot write. This depends on the agent's own standing instructions - another sub-agent refused even with a named output path. So name the file as the deliverable and always give a fallback. (Evolutionary Media Commons, 2026-10; Kosmosis, 2026-10; DataWizard, 2026-10)
- **"Preserved in git history" is false until the vault is saved.** An editing sub-agent cut two sections for size and wrote that the full text was in the note's git history, but no commit had run since the draft was written, so the cut text existed only in the agent's context. When you cut text for size, move it word for word into a sibling archive note in the same step. Never point at git history for text written in this session. (Kosmosis, 2026-10)
- **Staged files stay in the container that staged them.** A sub-agent that was cancelled, or that ran in a different container from the lead, leaves its `/mnt/user-data/outputs/` staging behind; the lead seat re-stages (hash-checked) instead of assuming the files are there. (Holonic Canvas, 2026-10)
- **Parallel sub-agents share the user's Chrome, and bulk reads can trip a site's bot check.** Four research agents used one Chrome while the lead used it too; one agent's bulk reads of a property portal triggered the site's slider check for the lead and for the user as well. Give browser-using agents a throttle, or keep the browser work in the lead. Research sub-agents that had web search and fetch but no browser did not hit this: three ran in parallel for 8, 13 and 37 minutes, and each wrote its CSV or markdown deliverable to the scratchpad as asked. (LocationScout, 2026-10; the web-only run seen once)
- **A worker's own count check can pass while a file is missing.** A fast-tier staging worker listed a folder, staged its `.md` files, and reported "313 selected, 313 staged". The listing held 314. One file never made it into the worker's selection, and the check compared the staged count with that same selection. The gap showed up only later, in a fixture run (a projection whose core was absent). Compare the staged count with the source listing, filtered the same way, never with the worker's own list. (DataWizard, 2026-10)
- **When parallel agents must put the same string in many files, one file owns it and they copy it from that file.** An agent that retypes a shared line (a footer, a fixed block, a template line) drifts from the canon wording. In one build, the builder's retyped line differed from the canon spec and would have landed in 92 notes. Keep the string in one file in the scratchpad. Brief each agent to read it there and paste it, never to retype it. Check the result with a byte compare against that file. (DataWizard, 2026-10)
- **The permission classifier can deny the lead's edit to a shared file while a sub-agent's edit to the same file passes.** In one session the lead's own edit to a shared coordination file was denied ("Modify Shared Resources"). An installer sub-agent's edit to the same file ten minutes earlier had passed. Each call is judged on its own, so the same write can get different answers. Do not loop on the denied call. Ask the operator to approve it or make the edit, then verify the file on disk. (DataWizard, 2026-10)

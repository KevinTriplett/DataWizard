# 8.0 Device Bridge

*Staging, commits and transport: [[8.1 Device Bridge - Staging, Commits and Transport]]. Sub-agents and orchestration: [[8.2 Device Bridge - Sub-agents and Orchestration]].*

- **Native-Mac contexts are out of reach from the device shell.** The device shell is a Linux sandbox mounting only the connected folders. It cannot reach the Mac's native filesystem outside them (`~/Library/LaunchAgents`, system paths), cannot run macOS tools (`launchctl`, `osascript`, `sfltool`), and cannot read the macOS Keychain or app-private data outside the mounts (the Signal desktop database, for example: its Keychain-backed decrypt is a native-Mac operator step, never a bridge step). Native machine-state work - launch agents, notifications, system settings, Keychain-backed decrypts - must be handed to the operator as a complete, literal Terminal command plus a verification command. The bridge confirms a native job only by its side effects: a native scheduler (launchd) cannot be inspected from the shell, so an advancing stream cursor or a new file on the mount is the only bridge-visible proof that the job ran. Siblings of this rule: `device_bash` localhost is the VM's (below); git over SSH is operator-native (MCP Reliability guide); no `sqlite3` CLI (below). (DataWizard, 2026-09)
- **`Control_Chrome` proxy: tab management works; page reads do not.** `list_tabs` / `open_url` / `switch_to_tab` are reliable, but `get_page_content` AND `execute_javascript` return "Google Chrome is not running" even with a live tab (intermittent in DW S230; consistent in LS S73). To read a live, logged-in page (e.g. Google Maps saved lists), use the **claude-in-chrome extension** instead -- once the user signs in, its screenshots + accessibility-tree DOM are reliable. Verify page state via `list_tabs` URL params, not by retrying the read. (Source: DW S230, Location Scout 2026-08)
- **`device_bash` backgrounded processes do not survive the call** *(unreliable in both directions - see the 2026-09 correction at the end of this bullet)*. Like the sandbox, a server started on the user's machine via `device_bash` with `&`, `nohup`, or even `setsid` is gone by the next `device_bash` call (same-shell `curl` 200, cross-shell 000 -- the call's process group is torn down on return). To exercise a device-side server, start it AND hit it within the SAME call; you cannot start it in one call and drive it from a separate browser/tool call. Test a device-hosted server this way, or (for a rendered-DOM check) stage the app into the sandbox and drive it with headless Playwright there. (Source: Location Scout, 2026-08) **Correction (DataWizard, 2026-09):** a `setsid python3 <http server> &` started in one `device_bash` call DID survive across later calls that day (answered curl minutes later; had to be killed explicitly). Treat persistence as undefined: never depend on a background process being there next call, and always kill what you started.
- **`device_bash` stops a call at ~180 s and kills its background jobs.** A `nohup setsid ... &` job left an empty log and no process a minute later. Run long work as resumable foreground batches, each under ~165 s, with state saved after every item so the next call picks up where the last one stopped. (LocationScout, 2026-10)
- **A `device_bash` that fails in every new session: the session disk inside the shell VM is out of file entries (inodes).** Each Cowork session gets its own Linux user and home folder (`/sessions/<user>`) on a fixed 10 GB session disk inside the VM (`sessiondata.img` in `~/Library/Application Support/Claude/vm_bundles/claudevm.bundle/` on the Mac). The app does not remove old session users or their home folders (none was removed in nine VM restarts; the user count only rose), so the disk fills over time. In one case 1,278 session users used all 655,360 inodes (`df -i /sessions` 100%) while 2.8 GB of space was still free. From then on every new session failed; only older sessions, whose users already existed, still had a shell - this is why earlier reports read the fault as per-session. Signs: every `device_bash` call fails with only "device_bash failed in the device workspace" (even a bare `echo`); `get_device_info` shows no `scratchFolder`; `device_list_dir`, `device_stage_files`, `device_commit_files`, the Obsidian MCP and the filesystem MCP all still work; every new session in every project on the computer fails, and an app restart or a new session does not help. The desktop app's VM log (`~/Library/Logs/Claude/coworkd.log`; the folder is protected, so the operator copies it into a connected folder to share it) shows `creating user rcw-<id> with home /sessions/rcw-<id>` with no `created user` line after it. To confirm, run `df -h /sessions; df -i /sessions` in an older session whose shell still works. Fix (operator, native Mac; every step can be undone): quit Claude with Cmd-Q or the menu Quit (closing the window is not enough); check that no program holds the file (`lsof` on `sessiondata.img` prints nothing); move `sessiondata.img` aside to a backup name, never delete it (it holds every old session's VM scratch files; keep it outside a synced folder unless a cloud copy is wanted, and allow up to 10 GB of disk for it); start Claude. In the one recorded case the app created a new, empty session disk at the next start, and the shell worked at once in a session that had failed for a day (`df -i /sessions` 1% after the swap). If the app does not create a new disk, move the backup back and report the fault. This is a workaround: with no cleanup in the app the disk fills again, so run `df -i /sessions` from time to time and plan the swap before it reaches 100%. (DataWizard, 2026-10)
- **Until the swap, work without the device shell.** A session whose `device_bash` fails once stays without a shell for its whole life; the tool itself says to stop after five failures - stop after two identical failures. Use the stage, edit in the container, commit path: stage the file, back it up by committing a copy to an archive folder, edit the container copy with a short Python read-modify-write, commit the result from a fresh outputs path with `expectedMtimeMs`, and verify by the size `device_list_dir` shows. Sub-agents can work the same way. When the build inputs are one staged bundle, rebuild in the container and check that the rebuild matches the staged outputs byte for byte before you change anything. To rebuild a generated file without the shell, find the notes newer than the last build by mtime in `device_list_dir`, stage only those, parse them with the project's own parser, and check that the embedded data round-trips byte-exact before splicing. Hand any step that needs a shell on the computer (git, native scripts, a database write) to the operator, and list the files left uncommitted in the handoff so a session with a working shell can commit them. (DataWizard, 2026-10; Holonic Canvas, 2026-10; Community Stack, 2026-10; Kosmosis, 2026-10; LocationScout, 2026-10; ReWoven, 2026-10; Rootland, 2026-10; MetaMyth, 2026-10)
- **SQLite cannot write on the mounted vault from `device_bash` -- the mount lacks file locking.** Creating or writing a SQLite db on a connected folder's mount fails with `disk I/O error` (WAL) or `attempt to write a readonly database` (even `mode=ro` opens, which still need the lock), because the VM's FUSE mount does not support SQLite's locking. Native processes on the user's machine are unaffected (WAL dbs on the same folder work normally there). Pattern: build/write the db in the VM `$HOME`, `PRAGMA wal_checkpoint` + close (or fold to `journal_mode=DELETE`), `cp` the closed file onto the mount, and verify by byte-hash plus a `file:...?immutable=1` read -- never a plain open. (Source: DataWizard, 2026-09)
- **Cowork connects folders individually, by exact path.** Connecting a parent folder does not expose its siblings, and moving or renaming a connected folder on disk breaks its connection until it is re-added in the desktop app. If a session suddenly cannot see a folder it could see before, check whether the folder moved before debugging the tools. (Source: DataWizard, 2026-07) The same rule hides vault-level files from `device_bash` when a session has only its project folder connected: the coordination board (`_Coordination/Board.md`), the Seed's `VERSION.md` and its skills were all unreadable there. The filesystem MCP (`read_text_file` on the Mac path) read them (Kosmosis, 2026-10). Where that server is broken (MCP Reliability guide, Verification Protocol Tier 1 caveat), request the folder (next bullet).
- **Folder grants: ask for the exact folder, but for a deep build path under a project folder ask for the project folder straight away.** `device_request_folder_access` can refuse a deep path with "contains characters the approval prompt can't display faithfully" even when nothing in it looks unusual (plain spaces and hyphens only). Depth alone is not the trigger - a request for a subfolder three levels down in a vault was approved at once in another session - so for a shallow target least privilege still holds: ask for the exact folder. But a deep build path under a project folder has been refused this way repeatedly while the project folder one level up was granted at once, so for that case ask for the project folder first. On any such refusal, fall back to the nearest parent the task can live with (granted one call later in one case; a request for the vault root itself was granted in seconds after a deep subfolder had been refused). One granted request was written with `~/` instead of the absolute `/Users/...` path, after checking the folder names with `device_list_dir` - a hint only, not isolated, since that request also widened to the parent. A second refusal form, "A requested folder can't be granted to this session", comes back with no prompt shown at all; the fallback that worked is the user adding the folder with "Add folder" in the desktop app. Adding the folder to the claude.ai Project does not connect it either - `get_device_info` still lists `connectedFolders: []` and the request is refused with no prompt (three sessions); the fix is the same Add folder step. A granted folder mounts under its own leaf name (`$HOME/mnt/<leaf-folder>`), not under its path inside the parent, so scripts must use the new mount path. The same tool is the clean way to give a reviewer sub-agent read access to another project's folder so it can see the source docs. (Evolutionary Media Commons, 2026-10; LocationScout, 2026-10; MetaMyth, 2026-10)
- **`device_request_delete_permission` always waits for a human answer, even inside an auto-approved scheduled task.** An unattended run that asks hangs (its task can read PENDING for hours). Unattended work tests deletes without a prompt - `touch` + `rm` of a scratch file - and skips the request; the rule lives under unattended automation in [[Cowork Scheduled Tasks]]. (Holonic Canvas, 2026-10)
- **No connected folder: the Obsidian MCP writes notes, and the Mac's `filesystem` MCP writes other files.** Until some folder is connected, `device_bash` and `device_commit_files` are unavailable. A large note can go in through the Obsidian MCP: write it in two calls (write, then append - mind the append-newline gotcha in **MCP Reliability and Write Verification**) and verify by file size and a known line offset. Real non-`.md` files (scripts, data) go in through the Mac's `filesystem` MCP, where its allowed directories include the vault. Check a retyped file by comparing `filesystem__get_file_info` size with the source's byte count (7 Python files, 80 KB, all exact). (MetaMyth, 2026-10)
- **`device_bash` localhost is the VM's, not the Mac's.** A `curl localhost:<port>` inside `device_bash` probes only the mount VM - connection refused (000) says nothing about servers the operator runs natively on the Mac. Never use the device shell to check whether a Mac-hosted server is up; ask the operator, or verify the change in the sandbox with a staged copy (see the headless-Chromium recipe below). (Source: Location Scout, 2026-09)
- **The device shell is GNU Linux, not macOS: `sed -i ''` (the BSD in-place form) fails with "can't read"; use `sed -i`.** Bare `sed -i` is fine on a connected folder; never the suffix form (`sed -i.bak`, `-i.tmp`) - the backup file it leaves cannot be removed without the delete grant; park a stray one in `_to_delete/` (Community Stack, 2026-10; DataWizard, 2026-10). For canon files past the MCP patch size threshold, a Python heredoc run in `device_bash` - read the live file, string-replace with an `assert` that the anchor exists exactly once, write, then parse the frontmatter back - landed multi-section edits in a 10K-word protocol file reliably where `patch_note` is unreliable. Verify with a YAML parse of the frontmatter after every such write. (DataWizard, 2026-10) The same shape sections a large file byte-faithfully: a 52KB log was read, sliced into shell + section files and written in one call. The safety net was a pre-split archive copy plus an assertion that the slices rejoin to the original bytes. No MCP patch is needed at any size (Kosmosis, 2026-10). Mac paths in notes (`/Users/...`) resolve only through `$HOME/mnt/<folder>/` (Community Stack, 2026-10).
- **`device_bash` turns `\uXXXX` text inside a command into the literal character.** A regex or JS escape written inline in the command arrives as the character itself. Write such escapes through a Python string built from a backslash variable, never inline. (DataWizard, 2026-10)
- **The bridge can drop mid-session and come back.** All `remote-devices` tools leave the tool list and return when the computer reconnects; a call that fails with "not connected to the bridge" landed nothing, but the link can also drop during a `device_bash` call ("Device disconnected before responding") while the command still ran to completion (LocationScout, 2026-10) - check on the device before retrying anything that writes. A sub-agent dispatched during a drop reports cleanly and can be resumed with the same instructions once the link is back. Verify before retrying (Rule 5); only a "not connected" error is a clean miss. (DataWizard, 2026-10; also Holonic Canvas, 2026-10)
- **A Project Instructions re-paste lands in a running thread at the next turn.** A thread that oriented on one PI version sees the new one after the next message; carry both sweep traces in the entry and run any new orientation sub-check late rather than pretending it ran. (Holonic Canvas, 2026-10)
- **No `sqlite3` CLI in the device shell.** Query a database on the mount with `python3 -c "import sqlite3; ..."` (read-only: `file:<path>?mode=ro` on a copy in `$HOME`). (DataWizard, 2026-10)
- **`pkill -f <pattern>` inside `device_bash` kills the shell itself.** The pattern matches the `bash -c` command line that carries it, so the call dies with exit 143 before its later commands run. Stop a device-side server you started in the same call by pid: `(python3 server.py & echo $! > $HOME/x.pid)` ... `kill $(cat $HOME/x.pid)`. (DataWizard, 2026-10)
- **Desktop-app Cowork artifacts have no web URL and freeze their data.** An artifact created in the desktop app lives only inside that app: no claude.ai link exists to embed or share, data baked in at build never refreshes, and pages that call MCP tools run only inside the app - as launchable or shared surfaces they are dead ends. `device_stage_files` with `artifact_ids` retrieves an artifact's current HTML by id for review or salvage; a proven exit is template + generator: keep the artifact's HTML as a page shell, re-inject fresh JSON from the source database with a small script, and serve the output as a plain local file. (Source: DataWizard, 2026-09)
- **Chat-delivered HTML previews run NO page scripts; published claude.ai artifacts run scripts but block external hosts.** A self-contained interactive HTML sent into the chat (SendUserFile) renders in the Claude app's preview as static markup only - every script is stripped, so a JS-driven page shows its empty skeleton and looks broken. Publishing the same page as a claude.ai artifact (Artifact tool) restores full JS on the page's own origin, but the artifact CSP blocks external requests for images and data (tile servers, APIs) - scripts from a few allow-listed CDNs such as cdnjs do load (LocationScout, 2026-10) - so the page must be fully self-contained and degrade gracefully when its network layers fail (a caught tile-error toast beats a broken map). Full fidelity - scripts AND network tiles - needs a real browser on a real file. Route accordingly: chat preview for static documents, published artifact for interactive review, local file for the real thing. (Source: Rootland, 2026-09)
